# i18n / l10n 注入契约（组件层）

> Status: Draft  
> Scope: 注入基础设施位于 `crates/ui-headless`；组件 strings 位于各自组件模块（`crates/ui-components`），并由 `UiRoot` 提供注入入口  
> Goal: 让基础组件的用户可见/可读屏文案可替换，同时避免中心化“大字典”导致的膨胀与冲突

## 1. 背景：为什么基础组件需要 i18n/l10n

基础组件并不是“纯视觉结构”，它们天然包含不可回避的**文字契约**，尤其是无障碍：

- 仅图标按钮（`IconButton`/`CloseButton`/`ClearButton`）必须有默认 `aria-label`，否则读屏不可用。
- 交互提示（如 `CodeBlock` 的 Copy/Copied）必须可读屏且默认可用。
- 导航控件（如 `Pagination`）默认文案影响可访问性与可测试性。

如果把这些默认文案硬编码为英文：

- 组件将“开箱可用”与“可本地化”二选一。
- 后期补丁会引发 API/测试/文档/E2E 大范围回归与迁移成本。

因此这里的目标不是“现在就实现翻译系统”，而是**先把文案来源抽象为注入点**：默认值存在，但可被覆盖。

## 2. 非目标（Non-goals）

- 不定义“翻译引擎”（key-based lookup / ICU / 资源加载）。
- 不负责应用级语言切换状态机。
- 不强绑定任何异步运行时或序列化格式。

## 3. 设计原则

### 3.1 组件默认可用，但文案可替换

文案来源优先级（从高到低）：

1. 组件显式 props（调用方传入的 `aria_label` / `clear_label` 等）。
2. `UiRoot` 注入的 i18n bundle（全局/局部策略）。
3. 组件内置默认值（英文兜底，保证开箱可用）。

### 3.2 避免中心化“大 struct / 大文件”

不使用一个包含“所有组件全部文案字段”的 `UiI18n { action_bar: ..., date_picker: ... }`：

- 该结构会随着组件数量线性膨胀；
- 合并冲突频发（多人同时改同一文件）；
- 即使启用组件级 feature gate，中心大表仍会把不相关字符串带入编译/链接路径。

正确做法是：

- `UiI18n` 只做**bundle registry**（类型擦除的容器），不包含所有组件字段。
- 每个组件在自己的模块内定义 `XxxStrings`（只包含该组件所需文案）。
    - 调用方按需覆盖：`UiRoot i18n=ui_headless::UiI18n::default().with_strings(ActionBarStrings { ... })`。

### 3.3 Tree-shaking 友好

- 每组件的 `XxxStrings` 定义应放在该组件模块中，跟随 `component-*` feature gate；
- registry 本身是常驻基础设施，但不引入组件级 strings 类型依赖；
- 未启用组件 feature 时，其 strings 类型不会参与编译。

## 4. 结构方案（推荐）

### 4.1 `UiI18n`：类型擦除 bundle registry（`ui-headless`）

- `UiI18n` 内部持有 `HashMap<TypeId, Arc<dyn Any + Send + Sync>>`；
- `with_strings<T>` 以 `TypeId::of::<T>()` 存入覆盖值；
- `strings<T: Default>` 读取覆盖值，缺失时回退 `T::default()`；
- `UiRoot` 通过 `provide_context(UiI18n)` 提供给所有组件（注入类型来自 `ui-headless`）。

### 4.2 `CommonStrings`：跨组件复用的最小集合

跨组件通用（且必须可覆盖）的文案可放入 `CommonStrings`（例如 Loading/Close/Clear）。

注意：`CommonStrings` 只应包含真正“跨组件通用”的字段；组件专属文案仍应归属组件模块。

## 5. l10n（格式化）注入的后续扩展

对于日期/数字/货币等格式化能力，建议采用类似的“策略注入”：

- `DateTimeFormatter` / `NumberFormatter` 等 trait 或闭包策略；
- `ui-state-primitives` 只建模状态，不做格式化；
- `ui-components` 仅消费注入策略。

这部分属于后续规格，不在本 spec 中冻结实现细节。

## 6. 测试建议

- 单元测试：验证默认文案与“自定义来源标记”（如 `data-*-source`）的稳定性。
- 语义测试：验证 `aria-label`/`role`/`data-slot` 等契约。
- E2E：用稳定语义选择器断言关键交互流，并可选验证 debug overlay/trace 事件可回放。
