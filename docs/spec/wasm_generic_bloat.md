# WASM 泛型膨胀治理（Generic Bloat Control）

## 问题定义

Rust 泛型采用单态化（Monomorphization）。

当逻辑层把泛型扩散到高频组件路径时，例如：

- `ButtonLogic<u32>`
- `ButtonLogic<String>`
- `ButtonLogic<MyStruct>`

编译器会为每个具体类型生成独立机器码。  
在 WebAssembly 目标下，这会直接推高包体，影响首屏加载与交互启动时间。

## 核心判断

- 对 WASM UI 组件库，体积通常比纳秒级 CPU 优化更优先。
- 不要把“泛型洁癖”当成默认设计。

## 设计策略

### 1) 默认瘦逻辑（Thin Logic）

- `logic.rs` 优先处理具体类型：`bool`、`enum`、`f64`、明确的状态结构体。
- 只有在“跨组件/跨场景确有复用收益”时，才引入泛型。

### 2) 优先收敛核心接口的泛型扩散

- 在核心行为接口上，优先考虑动态分发边界（如 `&dyn Trait`）以限制单态化膨胀。
- 允许小额 vtable 开销换取稳定包体。

### 3) 泛型只放在必要边界

- 可接受：`List<T>`、数据容器、明确的通用算法层。
- 不可接受：组件核心交互逻辑为“泛型而泛型”，导致单态化乘法扩散。

## 分层约束

- `logic.rs`：
  - 应避免将泛型类型参数直接穿透到组件核心行为路径。
  - 需要通用能力时，优先在边界层做适配，再落回具体化状态更新。
- `view.rs`：
  - 不承担泛型膨胀治理；只消费已经收敛的逻辑输出。

## 验收与门禁建议

- 为关键组件建立最小特性构建检查（`--no-default-features`）。
- 使用特性树与体积预算守卫（见 `docs/spec/tree_shaking.md`）。
- 代码审查必须回答：
  - 这个泛型是否真的必要？
  - 是否存在收敛到 `dyn` 或具体类型的更小方案？
  - 是否会在 WASM 产物上放大单态化代码体积？

## 反模式

- 在组件核心逻辑层无差别使用 `T: Trait`，而没有体积收益评估。
- 把多个业务路径都参数化，造成组合爆炸。
- 明知仅有少量固定类型输入，仍强行保持“完全泛型”API。
