# 架构热寂治理（Compile-time Evolution & Automated Migration）

## 问题定义

协议长期演进后，若只增不减地保留 `v1/v2/v3` 运行时兼容分支，会导致：

- `logic.rs` 版本分支膨胀（`match version` 层层叠加）
- 新开发者与 Agent 无法判断应使用的协议版本
- 旧版本永不淘汰，系统复杂度持续熵增

最终进入“热寂”：没人敢删旧逻辑，也没人敢安全演进。

## 核心判断

- 协议演进必须“编译期可治理”，而不是“运行时永久兼容”。
- 系统生命力来自可遗忘能力：可迁移、可弃用、可删除。

## 标准解法

### 1) Schema Registry（版本注册表）

建立全局注册表，登记：

- 组件协议名
- 当前稳定版本
- 受支持版本窗口
- 迁移路径（`vN -> vN+1`）

注册表必须机器可读，供 lint/codemod/CI 统一消费。

### 2) Transform Functions（纯函数迁移）

每次升级必须同时提交迁移函数：

```rust
fn migrate_v1_to_v2(old: ProtocolV1) -> ProtocolV2
```

要求：

- 纯函数、可测试、可组合
- 支持链式迁移（`v1 -> v2 -> v3`）
- 迁移失败可诊断（结构化错误）

### 3) Codemods（自动代码重写）

工具链必须提供 codemod：

- 扫描仓库中旧协议调用点
- 自动重写到新协议 API
- 对静态配置执行同版本迁移转换

目标是把“升级成本”从人工逐点改造变为可重复自动化流程。

### 4) 生命周期淘汰策略

- `vN+1` 发布：`vN-1` 标记 `deprecated`
- `vN+2` 发布：移除 `vN-1` 支持并触发编译失败
- 兼容窗口必须文档化且可预测，禁止无限期拖延

## 分层约束

- `logic.rs`：
  - 允许：当前版本与有限窗口版本适配
  - 禁止：无限期保留历史版本分支
- 工具链/infra：
  - 允许：codemod + lint + CI 阶段阻断旧版本使用
  - 禁止：仅靠人工约定维持版本健康

## 验收要求

- 每次协议升级 PR 必含：
  - 版本注册表更新
  - 迁移函数与测试
  - codemod 规则更新（或明确 N/A）
  - 弃用窗口说明
- CI 必须在超过支持窗口的旧协议出现时直接失败。
