# 平台退位与生态自演化（Platform Abdication）

## 问题定义

组件库一旦成功，业务团队会在其上构建垂直领域原语（如金融/医疗/运营域）。  
若平台只提供“最终组件”，不提供“扩展工厂”，生态会出现：

- 各团队重复造轮子
- 垂直原语分叉且质量不一致
- 平台中心团队成为扩展瓶颈

## 核心判断

- 架构的终局不是“所有组件都由核心团队维护”。
- 架构的终局是“核心团队可以退位，生态仍能按同一质量法则自增长”。

## 标准解法

### 1) 交付重心从“产物”转向“生产系统”

核心交付优先级应从高到低为：

1. 哲学与治理文档（`philosophy` / `contributing` / 规则）
2. 脚手架与模板（如 `cargo-ui` / 组件模板）
3. 架构健身函数与 CI 免疫系统
4. 参考组件实现（Button 等）

### 2) 领域扩展的一等路径

为垂直领域原语提供标准扩展路径（如 `ui-financial-primitives`）：

- 统一目录契约
- 统一测试与语义标记契约
- 统一发布/版本治理策略

目标是“可扩展的秩序”，而不是“禁止扩展”。

### 3) 平台团队的“退位指标”

平台成功指标应包含：

- 社区/业务团队可独立创建高质量新组件
- 新组件默认符合分层与门禁
- 核心团队不介入也可完成从提案到落地

## 分层约束

- 核心平台层：
  - 负责规则、工具、脚手架、验证系统
  - 不垄断所有领域组件实现
- 领域扩展层：
  - 在统一法则内自由演化
  - 禁止绕过核心质量门禁

## 验收要求

- 至少提供一套可复用组件脚手架与贡献决策树
- `CONTRIBUTING`/治理文档与架构规则可被外部团队直接执行
- 新增领域组件仓或模块可通过同一套 fitness functions 与门禁
