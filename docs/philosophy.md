# rust-ui 哲学总纲

> Version: v1.0  
> Status: Active  
> Audience: 维护者、贡献者、架构与产品决策者

## 1. 文档目的

本文件是 `rust-ui` 的“哲学总纲”，回答以下核心问题：

- 我们在做什么。
- 我们为什么这么做。
- 我们如何做、如何做对。
- 什么是“高质量完成”。
- 与常见实现路线相比，我们的优势与代价是什么。

当文档之间有冲突时，默认优先级：

1. `docs/RULES_ZH.md`（硬规则）
2. `docs/spec/*.md`（规格冻结）
3. `docs/plan/*.md`（执行计划）
4. 本文（哲学整合与决策理由）

## 2. rust-ui

我们要构建的不是“组件数量最多”的库，而是一个 **可长期扩展、可验证、可迁移** 的 UI 平台：

- 具备 Spectrum 级别的分层架构严谨性（状态/行为/视图分离）。
- 具备 HeroUI 级别的工程易用性（可配置、可组合、上手成本可控）。
- 具备现代高质量交互手感（physics-first motion）。
- 具备 AI 原生开发友好性（强类型约束 + 编译反馈闭环 + 语义契约）。

一句话：**让正确性、可访问性、可维护性随着复杂度增长而不崩溃。**

## 2.1 目标应用场景（Target Application Scenarios）

为避免路线发散，我们明确优先场景：

- P0：复杂企业应用与后台工作流（表单、列表、选择、弹层、状态流转）。
- P1：数据密集型仪表盘（高频筛选、交互反馈、可视化联动）。
- P2：高交互工具类界面（更复杂编辑器/画布能力作为后续扩展）。

优先级策略：

- 组件与能力建设优先服务 P0/P1 的高频真实问题。
- 任何新增大型能力应能说明其对目标场景的直接价值。
- 当需求冲突时，以“目标场景覆盖率 + 架构一致性”决策。

## 3. 我们在做什么

`rust-ui` 是一个按职责分层的 workspace：

- `ui-core`：纯状态原语（Stately analogue）。
- `ui-headless`：交互与可访问性原语（Aria analogue）。
- `ui-theme`：设计 token 与 CSS 变量输出。
- `ui-motion`：动效引擎与执行后端。
- `ui-components`：最终组件层，组合前述能力。
- `apps/*`：可运行 demo/docs，作为验收面与回归面。

该架构天然面向多端演进：

- 当前主线是 Leptos CSR/WASM。
- 通过边界清晰与 feature gate，为 Tauri/WebView 场景保留稳定扩展路径。

## 4. 为什么要这样做

## 4.1 业界常见失败模式

大型 UI 库常见退化路径：

- 状态逻辑与视图耦合，改一处牵一发。
- 可访问性后补，成本高且容易漏。
- 样式与行为纠缠，重构风险极高。
- 动效散落在组件内部，无法统一治理。
- 参数命名与语义漂移，组件间心智模型不一致。
- 质量判断依赖“看起来可以”，而非可执行门禁。

## 4.2 我们的回答

我们用“架构边界 + 类型系统 + 语义契约 + 可执行门禁”来对抗复杂度：

- 状态可测试、可推理。
- 行为语义集中治理。
- 视觉层可替换、可主题化。
- 动效作为契约而不是零散技巧。
- 编译器和测试成为质量裁判。

## 5. 核心哲学

## 5.1 分层不可破

分层是本项目的第一性原则，而不是“代码风格建议”。

目标依赖方向：

- `core -> headless -> components -> apps`
- `theme` 与 `motion` 作为基础设施横向服务，不反向侵入业务层。

边界收益：

- 降低组件数量增长后的系统性失控概率。
- 让每层问题可以独立定位与修复。
- 降低重构时的“全局回归半径”。

## 5.2 类型优先，字符串次之

优先通过 enum/struct/规范化输入表达约束，而不是把语义留给字符串和注释。

收益：

- 无效状态更难被表示。
- 编译期更早暴露错误。
- API 可推理性更强。
- 对 AI 生成代码更友好（“填结构”优于“猜 DSL”）。

## 5.3 可访问性默认开启

A11y 不是“后期补丁”，而是原语层职责：

- 键盘语义、焦点语义、ARIA 语义由 `ui-headless` 与组件契约共同保证。
- 组件层负责正确装配，不允许把 A11y 当作可选装饰。

## 5.4 语义优先于样式技巧

状态必须可观测、可检索、可验证：

- 使用稳定 `data-*` 与 `aria-*` 标记表达状态和来源。
- 样式依赖显式状态，而非脆弱 DOM 结构猜测。
- 测试验证“语义契约”而不只验证视觉快照。

## 5.5 Motion 是契约，不是点缀

动效规则：

- 在组件层定义 motion contract。
- 在 `ui-motion` 执行实现。
- 尊重 `prefers-reduced-motion`。
- SSR / 非 wasm 路径必须安全降级。

这样做可以让“体验质量”可迭代，而不是每个组件独立发明轮子。

## 5.6 发布可用与开发效率并重

我们拒绝“只能发布不能开发”或“只能开发不能发布”的二选一。

- 对使用者：默认开箱可用。
- 对维护者：允许高效微调与快速验证。

## 5.7 质量必须可执行

“完成”不是主观描述，而是门禁通过：

- format/lint/test。
- SSR/WASM compile checks。
- demo/docs 可运行与契约覆盖。

## 5.8 文档是产品的一部分

文档不是附属物，而是契约载体：

- 规格定义行为边界。
- 计划定义执行顺序。
- docs app 定义可见能力与用法标准。

## 5.9 国际化（i18n）与本地化（l10n）默认纳入设计

我们将 i18n/l10n 视为与 A11y 同级的重要能力，而不是后期补丁。

原则：

- 组件内部不硬编码用户可见文案（或必须可被外部覆盖）。
- 可交互组件默认暴露文本与标签注入入口。
- 日期、数字、货币等格式化能力必须可外部策略化。
- 本地化能力的注入点应稳定、可测试、可追溯。

分层建议：

- `ui-core`：仅处理与语言无关的状态与规则。
- `ui-headless`：定义语义与格式化契约（不持有业务字典）。
- `ui-components`：消费外部 locale/formatter/messages 并渲染。

## 5.10 数据可视化兼容性是架构压力测试

`rust-ui` 虽以应用 UI 为主，但架构必须能容纳高复杂度可视化场景（例如未来 `ui-charts`）。

原则：

- 图表能力优先作为独立包演进（避免污染通用组件层）。
- 大数据量渲染不强绑 DOM 策略（允许 SVG/Canvas/WebGL 分工）。
- `ui-motion` 需支持数据驱动动画，不仅是微交互动画。
- 语义与可访问性在可视化场景仍需保底（例如描述、焦点、读屏降级路径）。

## 5.11 混合分发模型（Hybrid Distribution）是默认策略

我们采用“底层 package 分发 + 组件 source 分发”的混合模式，而不是全层 source-first。

默认分发边界：

- Package-first（稳定依赖层）：
  - `ui-core`
  - `ui-headless`
  - `ui-theme`
  - `ui-motion`
- Source-first（可定制表达层）：
  - `ui-components`（按需拉取具体组件源码）

设计理由：

- 用户想定制的是组件表达层，不应被迫维护整套底层原语源码。
- 底层能力通过 package 提供稳定契约与升级路径。
- 组件源码可读可改，AI 可直接基于真实业务上下文修复与迁移。

兼容性原则：

- 底层 package 视为稳定公共依赖，要求更严格 API 稳定性治理。
- source 组件必须声明其支持的底层 package 版本区间。
- 升级优先通过迁移脚本/兼容层完成，而不是依赖隐式“碰运气可编译”。

收益：

- 避免“只想用一个 Button 却要拷贝全栈源码”的依赖爆炸。
- 保留 shadcn-like 定制优势，同时控制底层兼容风险。
- 在 AI 场景下兼顾“可读源码”与“可控依赖”。

## 5.12 生态位目标：Leptos 先行，Rust UI 原语层可迁移

短期我们是 Leptos-first；长期目标是让关键原语具备跨框架复用潜力。

原则：

- `ui-core` 尽量保持框架无关抽象，不锁死到单一响应式实现。
- `ui-headless` 通过 adapter 层管理与具体 UI 框架的绑定。
- 把“框架耦合点”显式标注并控制在薄层边界内。

长期价值：

- 让 `ui-core`/`ui-headless` 有机会成为 Rust UI 生态的通用原语层。
- 降低未来迁移到 Dioxus/Iced/其他框架时的重写成本。

## 5.13 贡献者可成长性是一等约束

我们不仅服务维护者与使用者，也要系统性降低外部贡献者学习成本。

原则：

- 新贡献者可以在“局部任务”中逐步学习，而非一次理解全部分层。
- 贡献路径要有脚手架、决策树、样例 PR 与最小验收清单。
- 架构严格不应等于“高门槛劝退”。

目标：

- 让高标准与高参与度同时成立，避免项目演进只依赖核心维护者。

## 5.14 样式技术选型哲学：Token-first + 组件静态样式优先

我们明确默认范式：

- 组件层采用 token-first 的静态样式契约（`styles.rs` 聚合注入）。
- 状态切换通过语义标记（`data-*`/class）驱动样式分支。
- 运行时只传递必要 CSS 变量，不鼓励任意 inline style。

范式取舍：

- 默认不采用 Utility-First 作为组件库内部主范式。
- Utility-First 可以作为应用层（`apps/*`）快速布局手段，而非组件契约载体。
- CSS-in-Rust 不是默认路径，除非它在类型安全与构建成本上有明确净收益。

理由：

- 更稳定的语义-样式边界。
- 更易与 source-first/AI 读源码模式配合。
- 降低样式实现漂移和维护复杂度。

## 6. AI 原生哲学

## 6.1 战略假设

**Rust 强类型 + 编译反馈** 可以显著降低 AI 生成代码的幻觉成本。

相比“全靠 prompt 约束”，我们更依赖：

- 类型系统约束输入空间。
- 编译器/测试给出结构化反馈。
- 语义标记暴露机器可读状态。

## 6.2 在仓库中的落地形式

- 用类型化状态输入和 `logic.rs` 归一化替代分散 view 逻辑。
- 用 enum 限定 variant/size/mode 等离散状态。
- 用 `data-*` / source marker 暴露状态与来源。
- 用语义测试锁定关键契约，防止隐性回归。

## 6.3 人/Agent 共用路径

我们面向双读者：

- 人类开发者：稳定、易读、可组合 API。
- Agent/自动化：可解析、可验证、可追溯语义契约。

长期方向：

- 将当前分散语义标记进一步升级为统一 Agent Contract（Schema 化）。
- 让 Agent 不依赖脆弱 DOM 猜测即可理解组件意图与状态。

## 6.4 编译反馈闭环是默认工作流

推荐闭环：

1. 生成/修改最小 typed 变更。
2. 执行编译与门禁。
3. 基于诊断信息修正。
4. 循环直至契约与门禁同时通过。

## 6.5 流式（Streaming）是 AI 原生的交互基建

我们明确把流式能力定义为 AI 原生特征，而不是“可有可无的体验增强”。

流式不是只指“文本 token 逐字输出”，还包括：

- 结构流：`Spec/Config` 的分段产出与增量修正。
- 状态流：生成过程中的阶段状态（规划中、校验中、可预览、可提交）。
- 结果流：前端预览与语义标记的增量挂载。

为什么必须流式：

- 降低长任务等待成本，显著改善可感知响应。
- 让用户和 Agent 可以在中途纠偏，而不是“全量生成后一次性失败”。
- 让生成链路天然支持“边生成边校验”的工程模式。

工程要求：

- 流式输出必须可恢复（断流重连不破坏会话状态）。
- 流式片段必须可验证（分片不是绕过契约校验的通道）。
- 流式预览必须带状态标识（明确“草稿/已验证/可提交”）。

## 6.6 AI 配置直生组件（Config -> Component）是核心能力

我们将“AI 生成配置并在前端直接生成组件实现”定义为目标能力，而不是外围实验。

推荐双通道模型：

- 通道 A（运行时直出）：
  - AI 产出结构化 `UiSpec/ComponentSpec`。
  - 前端解释器按白名单组件与白名单属性即时渲染。
  - 用于秒级反馈、探索式搭建、交互草图。
- 通道 B（编译时固化）：
  - 将稳定的 `UiSpec` 转换为 Rust/Leptos 代码。
  - 经过 `cargo check` 与语义测试后并入组件实现。
  - 用于生产级稳定交付和长期维护。

关键约束：

- 配置必须有强 schema（类型、枚举、约束、默认值）。
- 配置生成必须有白名单边界（组件、属性、事件、样式能力）。
- 配置渲染必须有语义输出（`data-*`、ARIA、source markers）。
- 配置到代码的转换必须可追溯（谁生成、何时通过了哪些校验）。

## 6.7 Agent Contract 必须版本化与可迁移

一旦 Agent 开始消费 schema，它就是公共 API，必须像组件 API 一样治理版本。

原则：

- 明确 `schema_version`，并对破坏性变更执行版本升级。
- Agent 与 UI 交互前可协商/声明支持版本区间。
- 提供兼容策略：并行支持窗口或显式迁移工具，不做“静默破坏”。
- 文档和测试必须覆盖版本差异与降级行为。

最低治理要求：

- 变更日志记录 schema 变更类型（新增/弃用/破坏性）。
- 为关键版本提供迁移说明（旧字段到新字段映射）。

## 6.8 AI 诊断适配器（Compiler Diagnostics Adapter）是必要中间层

我们不假设 LLM 能稳定消费完整 `rustc` 原始输出。

因此需要中间层将编译/测试诊断压缩为结构化对象，最小包含：

- 错误代码。
- 文件与位置。
- 期望类型与实际类型。
- 相关上下文片段。
- 可执行修复建议（机器可消费）。

目标：

- 提升 AI 自修复成功率。
- 降低 token 噪音与错误聚焦失败概率。
- 让生成闭环从“文本猜测”升级为“结构化诊断驱动”。

## 6.9 AI 行为生成必须在受限沙箱内执行

`UiSpec` 解决结构生成，但行为生成同样关键且风险更高。

原则：

- AI 不直接生成任意可执行前端代码作为默认路径。
- AI 行为通过受限 `Action` 集合表达（如 `Validate`、`Fetch`、`Navigate`、`SetState`）。
- 运行时执行器只解释白名单动作及其组合，不执行任意脚本。

目标：

- 在保证可编排能力的同时，把安全边界前置为架构约束。

## 6.10 Agent Contract 需要能力协商（Capability Negotiation）

仅有版本号不足以应对真实多 Agent 生态。

我们要求：

- Agent 在会话前声明支持的版本区间与能力集。
- UI 端返回可用能力矩阵，双方选择可互通的最高能力集合。
- 协商失败时给出可诊断降级路径，而不是静默失败。

这可显著降低“向后兼容地狱”的实际摩擦。

## 6.11 AI 校验链路采用“预检 + 重检”双层策略

仅依赖 `cargo check` 会在高频 AI 微调中带来成本压力。

策略：

- 预检层：轻量语法/类型快速检查（例如基于 rust-analyzer 能力）。
- 重检层：`cargo check` + 质量门禁作为最终裁决。

目标：

- 用低成本过滤大部分低级错误。
- 把昂贵校验资源留给高价值候选结果。

## 6.12 沙箱策略配置（Policy Configuration）必须细粒度

Action 白名单只是第一层，真正安全边界由策略配置决定。

`Fetch` 最低策略要求：

- 仅允许白名单协议（默认 `https`）。
- 仅允许白名单域名/路径前缀。
- 支持方法、头、频率、超时上限约束。
- 对 Tauri/本地资源路径默认拒绝，除非显式授权。

`SetState` 最低策略要求：

- 仅允许修改被授权状态作用域（scope）。
- 禁止跨域写入无关全局状态。
- 支持字段级白名单或 capability 标签约束。

原则：

- 安全策略由应用显式声明，运行时强制执行并可审计。
- 没有策略配置的动作能力视为默认关闭。

## 7. 我们怎么做

## 7.1 默认交付方法

1. 先冻结目标与非目标。
2. 先做薄切片（vertical slice），再扩功能面。
3. 严守分层边界。
4. 用语义测试锁定行为契约。
5. 通过门禁后再扩展规模。

## 7.2 组件实现模板

标准组件结构：

- `logic.rs`：参数归一化、派生状态、来源标记。
- `view.rs`：结构渲染、attrs/handlers 装配。
- `styles.rs`：静态样式契约。
- `motion.rs`：动效契约与绑定。
- `mod.rs`：最小稳定导出面。

## 7.3 API 演进策略

优先策略：

- 向后兼容的增量演进（但是目前仍属于最初开发阶段，为了正确可以不考虑兼容, 主版本冻结前允许必要破坏）。
- 统一命名语义（如 `is_*`、`on_*`、`default_*`）。
- 受控/非受控成对设计。
- 默认值来源单一（logic 层归一）。

## 7.4 AI 原生实现流水线（Streaming + Config）

建议将 AI 生成能力落为标准流水线，而非临时脚本：

1. 指令输入。
2. 流式产出 `UiSpec`（持续可见，支持中途纠偏）。
3. `UiSpec` schema 校验（字段、枚举、依赖关系、默认值注入）。
4. 前端运行时渲染预览（白名单解释器）。
5. 语义契约检查（ARIA、`data-*`、交互可达性最小约束）。
6. 可选固化：`UiSpec -> Rust/Leptos` 代码生成。
7. 编译与门禁（`cargo check/fmt/clippy/test`）并回写诊断。
8. 通过后落地到组件层或示例层。

实施原则：

- 先把 `Spec` 做稳，再扩大组件白名单。
- 先跑通“可解释 + 可校验 + 可回滚”，再追求生成范围。
- 任何运行时直出能力都不能绕过安全与语义边界。

## 7.5 开发者体验（DX）最后一公里

我们明确要求“做得对”与“做得快/爽”同时成立。

DX 基线能力：

- 样式热重载：优先支持无需重编译 wasm 的样式迭代路径。
- 组件热开发：组件修改后尽可能保持上下文，减少交互流程重走成本。
- 状态保持策略：在热重载路径中提供可选状态保留机制，用于复杂交互调试。
- 组件工作台（Workbench）模式：提供隔离画布，支持快速切换 props、状态矩阵和交互场景。

实现方向：

- 将验收型 apps 与开发型 workbench 分工，避免单一入口同时承担所有目标。
- 把“视觉微调心流”视为工程效率指标，而不只是体验偏好。

## 7.6 生态互操作与“胶水层”策略

我们将与 Rust 生态关键基础设施的互操作视为架构能力，不是后置集成。

关键胶水层：

- `serde`：`UiSpec` 的序列化/反序列化、版本迁移与错误报告标准化。
- `tracing`：定义统一 span/event 语义，贯穿状态、交互、生成、渲染链路。
- async：避免把 `ui-core`/`ui-headless` 绑定到单一运行时（tokio/async-std）。

要求：

- 异步能力通过抽象边界暴露，不把 runtime 细节泄露到上层 API。
- 追踪语义在核心层就定义，避免各组件各说各话。

## 7.7 全局状态管理可扩展策略

组件内状态与应用级状态必须分层治理。

原则：

- `ui-core` 提供可组合状态原语，不强制单一全局状态框架。
- 应用层可选接入全局状态方案，但必须保持与 `ui-core` 契约一致。
- 跨页面/跨区域状态同步要有明确桥接层，不让组件直接依赖业务 store 细节。

目标：

- 在大型应用场景下保持状态模型可演进、可测试、可替换。

## 7.8 测试金字塔与 E2E 可执行策略

我们将测试分层明确化：

- 单元测试：`ui-core` 纯逻辑与状态机。
- 集成测试：`ui-headless + ui-components` 的交互契约验证。
- E2E：真实浏览器场景下的端到端回归。

E2E 基线要求：

- 稳定语义定位标记（如 `data-*`/语义标记）用于自动化选择器。
- 为 WASM 场景提供稳定测试钩子与等待策略，降低脆弱性。
- 把关键业务流纳入 Playwright/Cypress 等工具的可重复回归集合。

## 7.9 贡献者开发工具链：脚手架与决策树

我们要求提供“贡献者友好”的默认工具链。

最低能力：

- 组件脚手架工具：一键生成 `logic/view/styles/motion/mod` 模板与必填 TODO。
- 贡献者决策树：按任务类型指引改动入口与边界（样式/语义/行为/状态）。
- PR 自检模板：在提交前提示必须完成的契约与测试检查。

目标：

- 把隐性经验显式化，减少“第一次贡献靠猜”。

## 7.10 异步操作与数据流契约

组件库必须对异步交互给出统一模式，避免每个组件各写一套 loading/error 语义。

原则：

- UI 组件状态（如 `is_loading`）与业务异步状态边界清晰。
- 提供可复用异步 action 原语（如 `use_async_action` 方向），统一状态语义。
- `aria-busy`、禁用态、重试态等交互反馈与异步状态保持一致映射。
- 与应用数据层（如 `create_resource`/query 类方案）通过适配层协作，不相互绑死。

目标：

- 让异步流程可组合、可测试、可追踪、可迁移。

## 8. 我们怎么做好

## 8.1 “好变更”的定义

一个变更应同时满足：

- 架构正确（边界不破）。
- 行为正确（状态与交互语义成立）。
- 可访问性达标（默认可用）。
- 可测试（契约可断言）。
- 可维护（命名和模式一致）。
- 可解释（人和自动化都能读懂）。

## 8.2 每次关键改动的检查清单

- 改动是否在正确层？
- 命名是否与全库一致？
- 无效状态是否被限制或归一化？
- 是否暴露了必要语义标记？
- 是否覆盖 reduced-motion / SSR / wasm 分支？
- 文档与示例是否同步更新？
- 门禁是否完整通过？

## 8.3 明确禁止的反模式

- 在 `ui-core` 写 DOM/样式逻辑。
- 在 `ui-headless` 写视觉和动画编排。
- 在 `view` 层隐藏关键状态决策。
- 新增参数但不进入统一命名与契约体系。
- 公共 API 泄露底层实现细节类型。
- 用临时补丁破坏跨组件一致性。

## 8.4 调试与可观测性（Observability）要求

WASM 场景下，调试成本必须被系统性降低，而不是依赖 `console.log` 堆砌。

要求：

- 关键状态变更可追踪（来源、时间、前后值）。
- 关键交互事件可回放（按最小必要粒度记录）。
- 在开发模式提供可视化调试入口（信号/props/state 观测）。
- 调试能力默认不污染生产包体（开发特性开关隔离）。

建议方向：

- 建立 `devtools` 协议层，逐步靠近“组件树 + 状态流”可视化能力。
- 在 `ui-core`/`ui-headless` 增加可选 trace hooks，统一追踪接口。

## 8.5 运行时性能与内存剖析哲学

编译期正确性不等于运行时高质量。我们要求性能治理进入标准流程。

原则：

- 对关键组件定义性能预算（首次渲染、更新耗时、内存占用）。
- 在开发模式提供 profiling workbench（依赖图、更新次数、热点路径）。
- 性能回归要可检测、可归因、可阻断（至少对关键路径）。

实践方向：

- 用基准与回归曲线追踪关键组件性能。
- 将“慢但正确”视为未完成状态，而不是可接受终态。

## 9. 这么做的好处

## 9.1 工程好处

- 更高可靠性：契约化和类型化减少隐错。
- 更高可维护性：分层隔离减少耦合爆炸。
- 更强可回归性：语义测试可稳定兜底。
- 更好可重构性：边界清晰，替换成本可控。

## 9.2 产品好处

- 交互与可访问性一致性更高。
- 视觉和主题演进不必重写行为层。
- 随组件规模增长，质量更可控。

## 9.3 团队协作好处

- 评审标准更客观。
- 新成员上手路径更清晰。
- 讨论聚焦于“契约与边界”，减少空转争论。

## 10. 与其他实现路线对比

## 10.1 对比“单体组件库”

单体路线优点：

- 初期产出快。

单体路线问题：

- 规模增长后，行为/样式/状态纠缠，改动回归面巨大。

本路线优势：

- 初期稍慢，但中后期稳定性和迭代效率显著更高。

## 10.2 对比“样式先行”方案

样式先行优点：

- 视觉效果出得快。

样式先行问题：

- 语义和可访问性容易失真，长期维护靠经验而非契约。

本路线优势：

- 语义先稳，再放大视觉自由度；测试可验证而非靠主观验收。

## 10.3 对比“JS/TS 运行时灵活优先”

JS/TS 方案优点：

- 生态成熟、试错快。

JS/TS 方案常见代价：

- 运行时错误面更大，语义漂移更隐蔽。

Rust 路线优势：

- 编译期约束更强、回归发现更早、长周期演进更稳。

## 10.4 对比“完全 1:1 克隆 Spectrum API”

1:1 克隆优点：

- 迁移心智简单。

1:1 克隆问题：

- 复杂度极高，且不一定贴合 Rust/Leptos 语义。

本路线优势：

- 学习 Spectrum 的架构原则，而非盲目复制表层 API。

## 10.5 对比“HeroUI 风格参数极致扩张”

参数极致扩张优点：

- 业务方短期很爽。

参数极致扩张问题：

- 参数爆炸、语义漂移、维护负担快速上升。

本路线优势：

- 采用 Hybrid：语义底盘稳定 + 参数体验可控扩展。

## 10.6 对比“仅聊天式 AI 生成（无流式、无配置层）”

仅聊天式路径优点：

- 接入快，几乎零架构准备。

仅聊天式路径问题：

- 结果不可结构化校验，失败常在后置阶段暴露。
- 无流式中间态，用户只能“等最终结果”。
- 无配置层，无法稳定复现、回放、审计、固化。

本路线优势：

- 流式可见、可中断、可纠偏。
- 配置可校验、可追溯、可二次利用。
- 运行时探索与编译时固化形成闭环，兼顾速度与质量。

## 10.7 对比“严格哲学但无治理与逃生舱口”

纯刚性约束路线优点：

- 规则统一，短期内架构看起来很干净。

纯刚性约束路线问题：

- 遇到真实业务边角需求时缺乏落地通道。
- 外部贡献者不清楚如何提案与达成共识。
- 容易把灵活性外包给私有分叉，导致生态割裂。

本路线优势：

- 规则严格，但配套治理机制与受控例外通道。
- 让“坚持哲学”与“解决现实问题”可以同时成立。

## 10.8 对比“仅包分发优先”与“源码拉取优先（Shadcn-like）”

仅包分发优点：

- 接入简单，升级路径表面统一。

仅包分发问题：

- 黑盒兼容问题难以现场修复。
- AI 在缺少源码上下文时修复效率显著下降。
- 高定制业务容易被迫分叉。

混合分发策略优势：

- 底层稳定依赖由 package 承担，组件定制能力由 source 承担。
- 源码可读、可改、可审计，AI 可直接在真实上下文工作。
- 兼容问题可通过“版本约束 + 迁移脚本 + 诊断工具”工程化处理。

## 11. 我们接受的代价

- 前期设计与建模成本更高。
- 评审和门禁纪律更严格。
- Rust/WASM 开发链路下编译成本需要持续优化。
- API 扩展速度受“一致性约束”限制。

这些代价是有意接受的，因为它们换来的是长期可持续性。

## 12. 风险与缓解

主要风险：

- 编译速度影响迭代体验。
- Rust 前端生态相对年轻。
- 参数统一与组件扩张可能发生拉扯。

主要缓解：

- 薄切片 + 分阶段推进。
- 语义测试锁定关键行为。
- 文档和规格与实现同步演进。
- 保持默认门禁自动化执行。

## 12.1 社区贡献与治理模型

哲学要可持续，必须有治理与协作机制支撑。

最低治理要求：

- 明确贡献路径：问题分类、提案模板、PR 期望、验收门槛。
- 明确决策机制：谁有最终决策权，何时需要 RFC。
- 明确争议处理：技术分歧的评审与收敛流程。

治理目标：

- 让外部贡献在不破坏核心哲学前提下可规模化发生。

## 12.2 受控“逃生舱口”（Escape Hatches）

我们承认真实业务存在非理想需求，因此提供受控例外机制，而不是隐式破坏架构。

原则：

- 逃生舱口必须显式命名、显式风险提示、显式作用域。
- 默认关闭或低优先级，仅在必要场景启用。
- 使用后可被观测与审计，避免长期技术债隐蔽化。
- 不允许逃生舱口反向污染核心 API 语义。

建议命名与约束：

- 以 `UNSAFE_*` 前缀显式标识风险（例如 `UNSAFE_style_override`）。
- 需要开发期告警与文档标注“为何不推荐、何时可用”。
- 优先提供更安全替代路径（语义属性、slot class、token 覆盖）。

目标：

- 给工程现实留出空间，同时保护系统长期一致性。

## 12.3 架构决策记录（ADR）作为“判例法”

仅有规则不足以承载长期演进，关键取舍必须沉淀为可检索决策记录。

要求：

- 重大架构决策必须有 ADR（背景、候选方案、权衡、最终结论、影响面）。
- 被否决方案也要记录，避免历史重复争论。
- ADR 与代码、规格、迁移策略保持可追溯链接。

## 12.4 商业化与社区平衡原则

我们提前定义边界，避免未来生态撕裂。

原则：

- 核心原语与核心哲学保持开源、透明、可审计。
- 商业能力可构建在核心之上，但不反向锁死核心演进。
- 社区贡献路径与商业路线不能互相阻断。

目标：

- 在可持续投入与社区信任之间保持长期稳定平衡。

## 13. 成功指标

若以下指标持续改善，说明哲学有效：

- workspace 门禁通过率稳定。
- 语义/可访问性回归率下降。
- 组件 API 命名与状态契约一致性提高。
- 文档覆盖与 demo 覆盖持续提升。
- 新组件接入不破坏既有分层秩序。
- 外部贡献者首个 PR 的通过率与平均合并时长改善。
- 关键组件性能预算达标率稳定。
- AI 生成链路的首轮修复成功率持续提升。

## 14. 当前务实重点

- 继续强化状态与来源的语义契约。
- 推进代表组件参数模型统一。
- 明确目标场景驱动的组件优先级（P0/P1 优先）。
- 渐进增强 Agent 可消费语义（Schema 化方向）。
- 固化混合分发默认路径（core/headless/theme/motion 走 package，components 走 source）。
- 建立 `UiSpec` 最小可用 schema 与白名单解释渲染链路。
- 建立流式生成的阶段状态协议（生成中/已校验/可提交）。
- 建立 `UiSpec -> Rust` 的最小固化通路（先覆盖 Button/Select/Overlay）。
- 建立 AI 行为沙箱最小动作集（`Validate/Fetch/Navigate/SetState`）。
- 落地沙箱策略配置（Fetch 白名单 + SetState 作用域约束）。
- 设计 Agent 能力协商协议与握手流程。
- 建立“预检 + 重检”校验链路原型。
- 明确 i18n/l10n 注入契约（先覆盖文本、数字、日期三类能力）。
- 固化组件样式默认范式（token-first + `styles.rs`），并给出例外边界。
- 建立组件开发 Workbench（props 矩阵 + 状态矩阵 + 热重载体验）。
- 提供组件脚手架工具与贡献者决策树文档。
- 建立异步 action 原语与数据层适配边界。
- 设计诊断适配器原型（`cargo` 输出 -> 结构化 JSON）。
- 定义 `tracing` 语义与核心 span/event 规范。
- 明确 async runtime 解耦边界与 adapter 设计。
- 定义测试金字塔落地清单与 E2E 选择器规范。
- 启动性能/内存 profiling workbench 与关键预算基线。
- 定义 Agent Contract 的版本策略与迁移流程。
- 起草贡献与治理文档（Contributing + RFC 模板）。
- 建立 ADR 模板与目录规范。
- 设计受控 escape hatches 白名单与风险标注规范。
- 在不破边界前提下持续扩展组件能力。
